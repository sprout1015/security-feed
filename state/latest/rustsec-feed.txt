<h3 id="description">Description</h3>
<p>When writing an encrypted parquet file with a column with bloom filters, the header
and bitsets of the bloom filter are written in plaintext in the final parquet.</p>
<p>Patched versions now reject writing bloom filters when encryption is enabled, raising
an error at runtime.</p>
<p>Existing encrypted parquet files written with bloom filters are still vulnerable,
and it is recommended to rewrite those files with bloom filters disabled if possible.</p>
<p>Credit to Yanzhi Xin (autoCAT6) for finding this.</p>

<h3 id="description">Description</h3>
<h2>Who is affected</h2>
<p>Only applications that call <code>fork()</code> and then add private (encrypted) cookies
on the thread that forked, in more than one of the resulting processes. This
is an uncommon way to deploy a Rust web application. In particular:</p>
<ul>
<li>
<strong>Rocket is not affected.</strong>
</li>
<li>
<strong>axum is not affected as normally run.</strong> It is affected only when an
application forks worker processes itself and runs each on a
current-thread runtime. See &quot;Rocket and axum&quot; below.</li>
<li>Applications that never fork are not affected. This includes all
applications on Windows.</li>
<li>Signed cookies (<code>SignedJar</code>) are not affected.</li>
</ul>
<p>The exact conditions are listed under &quot;Conditions&quot; below.</p>
<h2>Description</h2>
<p>Private cookies are sealed with AES-256-GCM using a random 96-bit nonce.
Affected versions drew the nonce from <code>rand</code>'s thread-local generator,
<code>rand::thread_rng()</code>. That generator hands out bytes from an internal buffer
and only notices that the process has forked when the buffer is refilled. A
process that forks therefore continues, in both the parent and the child, from
the same buffered bytes, and the private cookies sealed first on each side of
the fork use the same nonces.</p>
<h2>Impact</h2>
<p>Reusing a nonce under the same key breaks AES-GCM. From two private cookies
that share a nonce, an attacker can:</p>
<ul>
<li>recover the XOR of the two plaintexts, and thus either plaintext if the
other is known, and</li>
<li>recover the GHASH authentication key and forge private cookies, with a
name and value of their choosing, that the application accepts as
authentic.</li>
</ul>
<p>The nonce is the first 12 bytes of a private cookie's (base64-decoded) value,
so a repeated nonce is visible to anyone who holds two such cookies.</p>
<p>Exploitation requires the uncommon deployment described above, and only the
first private cookies added after a fork are affected: at most 21 per process.
An attacker must obtain two of them, from two different processes.</p>
<h2>Conditions</h2>
<p>All of the following must hold:</p>
<ol>
<li>The target is a Unix-like system and the process calls <code>fork()</code> without a
subsequent <code>exec()</code>.</li>
<li>The thread that calls <code>fork()</code> used <code>rand::thread_rng()</code> at any point
before the fork. Any use counts, including <code>Key::generate()</code>, adding a
private cookie, or a call made by an unrelated crate.</li>
<li>After the fork, private cookies are added on that same thread in two or
more of the resulting processes: the parent and a child, or several
children.</li>
<li>Those processes use the same <code>Key</code>.</li>
</ol>
<p>When they hold, at most the first 21 private cookies added on that thread in
each process share nonces. After that the generator reseeds and the processes
diverge.</p>
<p>The following are <strong>not</strong> affected:</p>
<ul>
<li>Applications that never fork, including all applications on Windows.</li>
<li>Processes in which the forking thread did not use <code>rand::thread_rng()</code>
before the fork.</li>
<li>Private cookies added on threads that were created after the fork. This
includes servers that fork and then start a multi-threaded async runtime
in each child.</li>
<li>Signed cookies (<code>SignedJar</code>), which do not use a nonce.</li>
<li>Versions <code>0.12.0</code> through <code>0.13.3</code>, and <code>0.11.2</code> and earlier, which
obtained nonces from the operating system via <code>ring</code>.</li>
</ul>
<h2>Rocket and axum</h2>
<p>Rocket and axum were tested with <code>cookie</code>
<code>0.18.2</code> by collecting the private
cookies sent by each server process and comparing their nonces.</p>
<p>
<strong>Rocket</strong> (<code>0.5.4</code>, <code>CookieJar::add_private()</code>) is not affected. Rocket does
not fork, and it handles requests on worker threads of a runtime it creates
when launched. No nonce was reused:</p>
<ul>
<li>when launched normally, in a single process, or</li>
<li>when a parent process used a private cookie and then forked two worker
processes that each launched Rocket.</li>
</ul>
<p>
<strong>axum</strong> (<code>0.8.9</code>, with <code>PrivateCookieJar</code> from <code>axum-extra</code>
<code>0.12.6</code>) is not
affected as normally run. No nonce was reused:</p>
<ul>
<li>when run in a single process on a multi-threaded runtime, or</li>
<li>when a parent process used a private cookie and then forked two worker
processes that each started a multi-threaded runtime.</li>
</ul>
<p>An axum application is affected only if it does all of the following:</p>
<ol>
<li>forks worker processes itself,</li>
<li>runs each worker on a current-thread runtime on the thread that forked,
so that requests are handled on that thread, and</li>
<li>used <code>rand::thread_rng()</code> on that thread before forking.</li>
</ol>
<p>In that configuration, the first private cookies sent by two workers reused
nonces: 19 when the parent had added one private cookie before forking, and 15
when the parent had only called <code>Key::generate()</code>. No nonce was reused when
the parent did neither.</p>
<p>Other frameworks and libraries that use this crate's <code>PrivateJar</code> were not
tested. The conditions above apply to them as well.</p>
<h2>Fix</h2>
<p>Version <code>0.18.3</code> obtains nonces directly from the operating system's random
number generator, which is not affected by <code>fork</code>.</p>
<h2>Workarounds</h2>
<p>If upgrading is not possible, any one of the following prevents the reuse:</p>
<ul>
<li>Do not use <code>rand::thread_rng()</code>, directly or indirectly, on the forking
thread before forking. In particular, create the <code>Key</code> with <code>Key::from()</code>
or <code>Key::derive_from()</code> rather than <code>Key::generate()</code> before the fork.</li>
<li>In each child, immediately after forking, read and discard at least 256
bytes from <code>rand::thread_rng()</code> before adding any private cookie.</li>
<li>Add private cookies only on threads created after the fork.</li>
</ul>
<p>Applications that ran in an affected configuration should rotate their <code>Key</code>.</p>

<h3 id="description">Description</h3>

of the server name wasn't validated and the Matrix specification actually allows
the server name to have a maximum length of 261 bytes.</p>

<h3 id="description">Description</h3>
<p>With the default <code>avx2</code> feature on x86_64 and a CPU that supports AVX2,
<code>pqcrypto-dilithium</code> verifies signatures with PQClean's AVX2 implementation of
Dilithium. That implementation predates two upstream fixes
(<a href="https://github.com/pq-crystals/dilithium/issues/113">pq-crystals/dilithium#113</a>,
3 June 2026), the same ones described in RUSTSEC-2026-0586 for <code>pqcrypto-mldsa</code>:</p>
<ul>
<li>the verifier does not check that the infinity norm of <code>z</code> is below

are rejected with AVX2 and accepted by the portable code. This crate
implements a pre-standard version of the scheme, so the Wycheproof ML-DSA
vectors do not apply; the test signatures are built with the crate's own
signer.</p>
<p>The crate is unmaintained (see RUSTSEC-2024-0380) and no patched version is
expected. Disabling the <code>avx2</code> feature avoids the affected code.</p>

<h3 id="description">Description</h3>
<p>In affected versions, the <code>Fixed&lt;T&gt;</code> and <code>Dynamic&lt;T&gt;</code> wrappers (and the
<code>FixedNoClone</code> / <code>DynamicNoClone</code> variants in 0.6.x) did not wipe their contents
when dropped. The types implemented the <code>zeroize::ZeroizeOnDrop</code> marker trait,
which has no methods and does nothing by itself, but had no <code>Drop</code> implementation.
The documentation stated that secrets were zeroized on drop.</p>
<p>A secret held in one of these wrappers stayed in the freed stack or heap memory
after the wrapper went out of scope, where it could be read by anything able to
observe that memory later, such as a core dump, swap, or a separate memory
disclosure bug.</p>

wrappers on <code>T: Zeroize</code>, and adding <code>Drop</code> implementations that call
<code>zeroize()</code>. The first published release with the fix is 0.8.0-rc.1; the first
stable release is 0.8.0. All affected versions have been yanked from crates.io.</p>

<h3 id="description">Description</h3>
<p>On Windows, affected versions of this crate do not provide the intended security-enhancement.
In particular, any process running under the same user as the hardened process can reset our DACL,
and thus bypass the protection the DACL should have provided. Usage of the crate however <em>does not

<h3 id="description">Description</h3>
<p>In <code>url</code> 2.5.8 and earlier, <code>Url::origin()</code> handled a <code>blob:</code> URL by parsing its path as another URL and calling itself on the result. It did so regardless of the inner URL's scheme, <code>blob</code> included. Each <code>blob:</code> prefix cost one stack frame, with no limit on nesting depth. <code>Url::parse()</code> accepts a URL with 10,000 <code>blob:</code> prefixes followed by <code>https://example.com/</code> (50,020 bytes in total); calling <code>Url::origin()</code> on it overflowed the default 2 MiB stack of a spawned thread.</p>
<p>A stack overflow aborts the whole process, and <code>catch_unwind()</code> does not catch it. One such URL crashes any program that calls <code>Url::origin()</code> on untrusted input. <code>url::quirks::origin()</code> also calls <code>Url::origin()</code>. For example, Servo's <code>URL.origin</code> DOM getter calls <code>url::quirks::origin()</code>, so a script on a page can trigger the overflow.</p>
<p>
<code>url</code> 2.5.9 follows the URL Standard: <code>Url::origin()</code> takes the origin of the inner URL only when its scheme is <code>http</code>, <code>https</code>, or <code>file</code>, returns an opaque origin otherwise, and never calls itself. A <code>blob:</code> URL with another inner scheme that previously produced a tuple origin, such as <code>blob:ws://...</code> or <code>blob:blob:https://...</code>, now returns an opaque origin.</p>

<h3 id="description">Description</h3>
<p>
<code>tonic_middleware::IpKeyExtractor</code> is documented as rate limiting gRPC requests by client IP address,
but on a standard tonic server it keys on client-supplied <code>x-forwarded-for</code> and <code>x-real-ip</code>
headers. In 0.5.0–0.9.1, the extractor reads those headers directly; in 0.10.0–0.11.0, it first
checks for a bare <code>std::net::SocketAddr</code> request extension—which <code>tonic::transport::Server</code> never
supplies, as it provides <code>TcpConnectInfo</code> instead—and falls back to the same headers. Direct
clients can therefore choose their rate-limit key to bypass per-IP rate limits and increase the
number of tracked keys; without forwarding headers, 0.5.0–0.9.1 allow requests without limiting
them and 0.10.0–0.11.0 reject them by default unless <code>.fail_open()</code> is enabled.</p>
<p>Applications are affected if they use <code>GrpcRateLimitLayer</code> with <code>IpKeyExtractor</code> (the
<code>tonic-support</code> feature). The HTTP middleware's <code>IpKeyExtractor</code> reads <code>ConnectInfo&lt;SocketAddr&gt;</code> and
is not affected.</p>
<p>Version 0.11.1 fixes <code>IpKeyExtractor</code> to honor a server-supplied <code>SocketAddr</code> override first and then
read the TCP peer address from tonic's <code>TcpConnectInfo</code> (which <code>tonic::transport::Server</code> attaches
to plaintext connections and connections using its built-in TLS), without ever reading forwarding
headers. Deployments behind a trusted proxy can use the new opt-in <code>ForwardedIpKeyExtractor</code>, which
reads a single configured header (<code>x-forwarded-for</code> or <code>x-real-ip</code>) and is only correct when that
proxy sets the header as documented.</p>
<p>If you cannot upgrade to 0.11.1, use a custom key extractor that reads the peer IP from tonic's
connection information for the transport in use (including TLS) and rejects requests without a
verified peer address before invoking the limiter, or restrict backend access to a trusted proxy
that strips all incoming <code>x-forwarded-for</code> and <code>x-real-ip</code> fields and sets one <code>x-forwarded-for</code>
value to the verified client IP on every request.</p>

<h3 id="description">Description</h3>
<p>With the default <code>avx2</code> feature on x86_64 (non-Windows) and a CPU that supports
AVX2, <code>pqcrypto-mldsa</code> verifies signatures with PQClean's AVX2 implementation of
ML-DSA. That implementation predates two upstream fixes
(<a href="https://github.com/pq-crystals/dilithium/issues/113">pq-crystals/dilithium#113</a>,
3 June 2026):</p>
<ul>
<li>the verifier does not check that the infinity norm of <code>z</code> is below
<code>γ1 − β</code> (FIPS 204, Algorithm 8, line 13), so it accepts signatures that
conforming verifiers reject;</li>
<li>
<code>use_hint_avx()</code> mishandles a boundary case, so one class of valid
signatures is rejected.</li>
</ul>
<p>Creating an accepted out-of-bound signature requires the private key. The
practical effect is that verification results differ between this crate with
AVX2 and conforming implementations, including this crate without AVX2.</p>
<p>The Wycheproof ML-DSA verification vectors reproduce both defects: with AVX2,
37 / 41 / 49 invalid vectors (ML-DSA-44 / -65 / -87) are accepted and one valid
vector per parameter set is rejected.</p>
<p>The crate is unmaintained (see RUSTSEC-2026-0166) and no patched version is
expected. Disabling the <code>avx2</code> feature avoids the affected code. Migrating to a
maintained implementation, such as the <a href="https://crates.io/crates/ml-dsa">
<code>ml-dsa</code>
</a>
crate, is recommended.</p>

<h3 id="description">Description</h3>
<p>Someone who controls the content of a message with bare LF or CR line endings
can end it early with <code>\n.\n</code> on a server that takes a bare LF for a line
ending. What follows is read by the server as SMTP commands, which can be used
to send other messages over the same authenticated connection.</p>
<p>This affects messages passed to <code>send_raw</code>, and message bodies that are sent
without being encoded. The LF line endings of a <code>String</code> body are converted to
CRLF before it is sent.</p>

<h3 id="description">Description</h3>

<h3 id="description">Description</h3>
<p>A ZIP archive names each entry twice: in the local file header in front of the entry's data, and in the central directory at the end of the archive. <code>ZipArchive</code> lists and opens entries by their central-directory names. <code>ZipStreamReader::visit</code> and <code>ZipStreamReader::extract</code>, like <code>read_zipfile_from_stream</code>, read the local headers in order and use the local-header names without comparing them with the central directory.</p>
<p>An archive can therefore show one set of file names to code that inspects it with <code>ZipArchive</code> and write files under other names when it is extracted with <code>ZipStreamReader</code>. If an application checks an archive one way and extracts it the other way, an attacker can get files written or overwritten inside the destination directory that the check never saw.</p>
<p>The fix adds an opt-in check. <code>ZipStreamReader::enforce_header_consistency(true)</code> compares each local header with its central-directory entry (name, sizes, CRC-32, compression method, flags and modification time) and fails extraction on a mismatch; <code>ZipReadOptions::enforce_header_consistency(true)</code> and <code>ZipArchive::validate_header_consistency()</code> do the same for <code>ZipArchive</code>. The check is off by default, so upgrading alone does not change what <code>ZipStreamReader::new(...)</code> extracts: applications that extract untrusted archives with <code>ZipStreamReader</code> need to turn it on.</p>

<h3 id="description">Description</h3>
<p>With the <code>legacy-zip</code> feature, the decoders for the Shrink, Reduce and Implode compression methods reserved output capacity for the entry's declared uncompressed size before decoding anything. That size comes from the archive, and a ZIP64 entry can declare any 64-bit value, so reading or extracting a crafted entry of a few bytes panics with &quot;capacity overflow&quot; or fails a huge allocation.</p>
<p>An attacker who can supply an archive can stop a process that reads it, for example through <code>ZipArchive::extract</code>.</p>
<p>Only builds with the <code>legacy-zip</code> feature are affected; it is not enabled by default.</p>
<p>The fix caps the preallocation at 1 MiB, and such an entry now returns an error.</p>

<h3 id="description">Description</h3>
<p>For WinZip AES (AE-1 and AE-2) entries, the 10-byte HMAC authentication code was read and checked only after the reader had consumed exactly the entry's declared compressed size. If the archive ended before that size was reached, the read returned end-of-stream and the truncated plaintext was accepted without the check. The authentication code of an entry with no encrypted data was never checked.</p>
<p>AES-CTR ciphertext can be changed bit by bit without the password, and AE-2 entries carry no CRC-32, so an attacker who can modify an archive can alter the decrypted contents of such an entry without any error being reported.</p>
<p>This affects reading AES-encrypted entries with a password (for example <code>ZipArchive::by_name_decrypt</code>) with the <code>aes-crypto</code> feature.</p>
<p>The fix returns an error when the data ends before the declared size, and checks the authentication code of empty entries.</p>

<h3 id="description">Description</h3>
<p>Before writing an entry whose path goes through a symlink, <code>ZipArchive::extract</code> checks the symlink's target against the destination directory. That check compares the paths as text and does not follow symlinks, and from 7.2.0 it drops the root and prefix of an absolute target before comparing. Symlinks taken from the archive were created without any check of their targets.</p>
<p>A crafted archive can first create a symlink that points outside the destination, then a second symlink whose target looks like a path inside the destination but goes through the first one, and then a file entry under the second symlink. The file is written outside the destination directory, for example over an existing file in the user's home directory, and <code>extract</code> still returns <code>Ok(())</code>. On Windows, a target on another drive or share whose path otherwise matches the destination passes the check directly (creating symlinks there needs Developer Mode or administrator rights). The attacker has to know or guess the absolute path of the destination directory.</p>
<p>This affects <code>ZipArchive::extract</code> and <code>ZipArchive::extract_unwrapped_root_dir</code>.</p>
<p>The fix resolves symlink targets one component at a time from the canonicalized destination, following symlinks on the way, and refuses to create a symlink, or write through one, that leads outside the destination.</p>

<h3 id="description">Description</h3>
<p>RFC 5155 section 8.5 says a NODATA response proven with NSEC3 needs an NSEC3 record whose hashed owner name equals the hash of the query name, and whose type bitmap has neither the query type nor CNAME.</p>

<p>The fix treats such a response as bogus.</p>

<h3 id="description">Description</h3>
<p>When DNSSEC validation grouped a response's records into RRsets, it did not take the DNS class into account, and records of a class other than IN were left out before signatures were checked. If the IN records validated, the records of other classes (such as CH or HS) were marked secure too.</p>
<p>An attacker who can answer or modify DNS responses can add forged records of another class to a response and have them returned as validated. A forged DS record of another class can also get past validation, which lets any DNSKEY for the child zone be accepted and any answer from that zone be forged. How much this matters depends on how the application treats records of an unexpected class.</p>
<p>This affects DNSSEC validation through <code>DnssecDnsHandle</code> when built with <code>dnssec-ring</code> or <code>dnssec-aws-lc-rs</code>.</p>
<p>The fix rejects a whole response if any record in its answer, authority or additional section has a class different from the query's.</p>

<h3 id="description">Description</h3>
<p>Affected versions of <code>actix-http</code> skip a bare line feed (LF) inside an HTTP/1.1
chunked trailer instead of rejecting the invalid line ending. Trailer lines
must end with a carriage return and line feed (CRLF).</p>
<p>For example, after <code>0\r\nX\n</code>, the parser continues reading trailer data. If a
request follows on the same connection, its head can be consumed as part of the
trailer, so that request is never dispatched. If no more bytes arrive, body
decoding waits for more input instead of reporting an error. A remote client
can trigger these effects without authentication.</p>
<p>Request smuggling additionally requires an HTTP intermediary that forwards the
malformed body but uses a different request boundary. The tested HTTP
intermediaries either rejected the input or consumed and normalized it before
forwarding. Proxy access-control bypass, cache poisoning, and effects on other
users were not demonstrated.</p>
<p>Upgrade to <code>actix-http</code> 3.21.1 or later. The fix rejects bare LF and invalid
control bytes in trailers before consuming the following request, while
preserving partial reads and valid CRLF-terminated trailers.</p>

<li>
<code>&#62;=3.21.2</code>
</li>
</ul>
</dd>

<h3 id="description">Description</h3>
<p>Affected versions of <code>actix-http</code> apply the request header timeout only to the
first request on an HTTP/1 connection. When data arrives for a later request,
the dispatcher clears the idle keep-alive timer without starting a request
header timer.</p>
<p>A remote client without authentication can complete one request, send one byte
of a second request, and leave the connection open indefinitely without sending
more data. The same problem occurs when a complete pipelined request is followed
by a partial request in the same read. Repeating this can exhaust connection or
file-descriptor limits and prevent new connections from being accepted. The
effect depends on the server's resource limits and upstream connection controls.</p>
<p>Upgrade to <code>actix-http</code> 3.21.2 or later. The fix applies the configured request
header timeout to later partial requests, including those left in the buffer
after a complete pipelined request. Additional bytes do not renew the deadline.
The timeout covers request headers, not upload bodies.</p>
<p>If an upgrade is not possible, disable HTTP keep-alive, for example with
<code>HttpServer::keep_alive(KeepAlive::Disabled)</code> in <code>actix-web</code>. Connection limits
can reduce resource use but do not make stalled connections expire.</p>

<h3 id="description">Description</h3>
<p>Affected versions of <code>actix-http</code> do not track quoted strings when parsing
HTTP/1.1 chunk extensions. A carriage return inside a quoted extension value
is treated as the end of the chunk-size line, even if the closing quote is
missing. For example, <code>0;x=&quot;\r\n\r\n</code> is accepted as the end of a chunked body,
and a following pipelined request is dispatched on the same connection.</p>
<p>A remote client can trigger this without authentication. CR and LF are invalid
inside HTTP quoted strings, including after a backslash; they must be rejected
rather than interpreted as framing or accepted as quoted data.</p>
<p>Request smuggling requires an upstream intermediary that forwards the malformed
input while using a different request boundary. Dispatching two requests on the
sender's own connection does not by itself demonstrate an authorization bypass
or an effect on another user. Proxy bypass, cache poisoning, and cross-user
response mixing were not demonstrated by the reproduction.</p>
<p>Upgrade to <code>actix-http</code> 3.21.3 or later. The fix preserves quote and escape state
across reads and rejects invalid control bytes inside quoted strings and quoted
pairs before consuming the following body or request bytes.</p>
