<title>Security advisories: multiple vulnerabilities in Regexp and String case conversion</title>
<description>
<p>Seven vulnerabilities have been discovered in Ruby’s regular expression engine and in the case conversion of strings. We are aware of PoCs that prove some of them can be used to trigger remote code execution. We have released Ruby 4.0.10, 3.4.13 and 3.3.14 to fix them. We strongly recommend upgrading.</p>
<p>CVE identifiers have been requested for these vulnerabilities but have not been assigned yet, so this advisory refers to them by their GitHub Security Advisory (GHSA) identifiers.</p>
<h2 id="ghsa-34m4-m9fh-gqp5-heap-buffer-overflow-in-case-conversion-of-strings">
<a href="https://github.com/ruby/ruby/security/advisories/GHSA-34m4-m9fh-gqp5">GHSA-34m4-m9fh-gqp5</a>: Heap buffer overflow in case conversion of strings</h2>
<p>Ruby has a one-byte heap-based buffer overflow in the case conversion of strings. Changing the case of a crafted string may allow remote code execution. We are aware of PoCs that prove this flaw can be used to trigger RCE in some scenarios.</p>
<h2 id="ghsa-7x2q-68qv-6p8x-double-free-in-regular-expression-compilation">
<a href="https://github.com/ruby/ruby/security/advisories/GHSA-7x2q-68qv-6p8x">GHSA-7x2q-68qv-6p8x</a>: Double free in regular expression compilation</h2>
<p>Ruby has a double free in its regular expression engine. Compiling a crafted regular expression pattern may allow remote code execution in applications that compile attacker-controlled patterns. We are aware of PoCs that prove this flaw can be used to trigger RCE in some scenarios.</p>
<h2 id="ghsa-87fm-7w84-j2px-integer-overflow-in-case-conversion-of-strings">
<a href="https://github.com/ruby/ruby/security/advisories/GHSA-87fm-7w84-j2px">GHSA-87fm-7w84-j2px</a>: Integer overflow in case conversion of strings</h2>
<p>Ruby has an integer overflow in the case conversion of strings, which causes a heap-based buffer overflow. Changing the case of a crafted string may allow remote code execution. We are aware of PoCs that prove this flaw can be used to trigger RCE in some scenarios.</p>
<h2 id="ghsa-wpqw-5qxg-m68r-out-of-bounds-read-in-case-insensitive-regular-expression-matching">
<a href="https://github.com/ruby/ruby/security/advisories/GHSA-wpqw-5qxg-m68r">GHSA-wpqw-5qxg-m68r</a>: Out-of-bounds read in case-insensitive regular expression matching</h2>
<p>Ruby has an out-of-bounds read in its regular expression engine. Matching against a crafted regular expression pattern may allow remote code execution in applications that use attacker-controlled patterns. We are aware of PoCs that prove this flaw can lead to memory corruption in an attacker-controlled way.</p>
<h2 id="ghsa-3p8q-wmhx-vm2w-heap-buffer-overflow-in-regular-expression-compilation">
<a href="https://github.com/ruby/ruby/security/advisories/GHSA-3p8q-wmhx-vm2w">GHSA-3p8q-wmhx-vm2w</a>: Heap buffer overflow in regular expression compilation</h2>
<p>Ruby has an integer overflow in its regular expression engine, which causes a heap-based buffer overflow. Compiling a crafted regular expression pattern may allow remote code execution in applications that compile attacker-controlled patterns. We are aware of PoCs that prove this flaw can be used to trigger RCE in some scenarios.</p>
<h2 id="ghsa-7whj-cfh7-xgm4-heap-buffer-overflow-in-regexpto_s">
<a href="https://github.com/ruby/ruby/security/advisories/GHSA-7whj-cfh7-xgm4">GHSA-7whj-cfh7-xgm4</a>: Heap buffer overflow in Regexp#to_s</h2>
<p>Ruby has a heap-based buffer overflow in <code class="language-plaintext highlighter-rouge">Regexp#to_s</code>. Converting a crafted regular expression to a string may allow information disclosure or remote code execution in applications that compile attacker-controlled patterns. We are aware of PoCs that prove this flaw can be used to trigger RCE in some scenarios.</p>
<h2 id="ghsa-pvgc-g7gj-pv6h-out-of-bounds-read-in-case-insensitive-backreference-matching">
<a href="https://github.com/ruby/ruby/security/advisories/GHSA-pvgc-g7gj-pv6h">GHSA-pvgc-g7gj-pv6h</a>: Out-of-bounds read in case-insensitive backreference matching</h2>
<p>Ruby has an out-of-bounds read in its regular expression engine. Matching a crafted string may disclose memory contents or crash the process.</p>
<h2 id="affected-versions">Affected versions</h2>
<ul>
<li>Ruby 3.3.13 and earlier</li>
<li>Ruby 3.4.0 through 3.4.12</li>
<li>Ruby 4.0.0 through 4.0.9</li>
</ul>
<h2 id="recommended-action">Recommended action</h2>
<p>We strongly recommend upgrading to Ruby 4.0.10, 3.4.13 or 3.3.14.</p>
<p>Ruby 3.3 is in the security maintenance phase. Ruby 3.2 and earlier have reached their end of life and will not receive these fixes.</p>

<title>Regexp compilation fixes related to GitLab's CVE-2026-89078, CVE-2026-93577, CVE-2026-97229 and CVE-2026-110264</title>
<description>
<p>We have released Ruby 4.0.9, 3.4.12 and 3.3.13. They fix several bugs in Ruby’s regular expression engine (Onigmo) that GitLab found could be used for remote code execution on GitLab servers. GitLab published four CVEs for these issues, and the Ruby releases contain the fixes for the underlying bugs in Ruby.</p>
<h2 id="background">Background</h2>
<p>GitLab compiles regular expressions supplied by its users, such as patterns in CI configuration, with <code class="language-plaintext highlighter-rouge">Regexp.new</code>. GitLab found that specially crafted patterns could corrupt memory while Ruby compiles them, and that this could be turned into remote code execution on GitLab servers. GitLab addressed these issues in its own releases by patching the Ruby it ships, and assigned the following CVE identifiers:</p>
<ul>
<li>
<a href="https://www.cve.org/CVERecord?id=CVE-2026-89078">CVE-2026-89078</a>: Double Free issue in Regular Expression Parser (<a href="https://docs.gitlab.com/releases/patches/patch-release-gitlab-19-4-1-released/">GitLab 19.4.1</a>)</li>
<li>
<a href="https://www.cve.org/CVERecord?id=CVE-2026-93577">CVE-2026-93577</a>: Integer Overflow issue in Regular Expression Compiler (<a href="https://docs.gitlab.com/releases/patches/patch-release-gitlab-19-4-1-released/">GitLab 19.4.1</a>)</li>
<li>
<a href="https://www.cve.org/CVERecord?id=CVE-2026-97229">CVE-2026-97229</a>: Integer Overflow issue in CI/CD Regular Expression Compiler (<a href="https://docs.gitlab.com/releases/patches/patch-release-gitlab-19-4-2-released/">GitLab 19.4.2</a>)</li>
<li>
<a href="https://www.cve.org/CVERecord?id=CVE-2026-110264">CVE-2026-110264</a>: Integer Overflow issue in Regular Expression Compiler (<a href="https://docs.gitlab.com/releases/patches/patch-release-gitlab-19-5-1-released/">GitLab 19.5.1</a>)</li>
</ul>

<h2 id="who-is-affected">Who is affected</h2>
<p>These bugs are reached only when an application compiles a regular expression from a string that an attacker controls, for example by passing it to <code class="language-plaintext highlighter-rouge">Regexp.new</code>, <code class="language-plaintext highlighter-rouge">Regexp.union</code> or <code class="language-plaintext highlighter-rouge">Regexp.compile</code>, or by interpolating it into a regexp literal such as <code class="language-plaintext highlighter-rouge">/#{input}/</code>. Applications that only use regular expressions written by their own developers are not affected.</p>
<p>
<code class="language-plaintext highlighter-rouge">Regexp.timeout</code> does not protect against these bugs. Limiting the length of patterns does not reliably protect against them either, because some of them can be triggered by short patterns.</p>
<h2 id="recommended-action">Recommended action</h2>
<p>We recommend upgrading to Ruby 4.0.9, 3.4.12 or 3.3.13 or later.</p>
<p>If you cannot upgrade, please avoid compiling regular expressions from untrusted input.</p>
<p>Ruby 3.3 is in the security maintenance phase, in which we normally release only fixes for vulnerabilities. Ruby 3.3.13 includes these fixes as an exception, because GitLab assigned CVEs to issues that rely on them.</p>
<h2 id="about-cve-identifiers">About CVE identifiers</h2>
<p>Update (2026-11-20): The CVE identifiers of these vulnerabilities in Ruby are the ones GitLab assigned: CVE-2026-89078, CVE-2026-93577, CVE-2026-97229 and CVE-2026-110264. We requested separate identifiers for the Ruby advisories, but the CVE Program assigns a single identifier to a vulnerability in code that several products share, and GitLab is affected through the Ruby it ships. Please use these identifiers, together with the Ruby advisories listed in the table above, when you track these issues, for example in a security scanner. The CVE records currently list only GitLab as the affected product. We have asked GitLab, which maintains the records, to add Ruby to them.</p>
<p>Update (2026-11-17): We now treat these issues as vulnerabilities in Ruby. We have published a security advisory for each of them in the ruby/ruby repository, listed in the table above.</p>
<p>When we originally published this page, we had not requested CVE identifiers in Ruby for these fixes, for the following reason.</p>
<p>Ruby has generally considered it unsafe to compile and use a regular expression created from untrusted input. We stated this in the advisory for <a href="/en/news/2022/04/12/double-free-in-regexp-compilation-cve-2022-28738/">CVE-2022-28738</a>, where we nevertheless treated a double free in Regexp compilation as a vulnerability after a comprehensive assessment. We did the same for <a href="/en/news/2024/04/23/arbitrary-memory-address-read-regexp-cve-2024-27282/">CVE-2024-27282</a>.</p>
<p>However, the <a href="https://docs.ruby-lang.org/en/master/Regexp.html#class-Regexp-label-Timeouts">Regexp documentation</a> discussed untrusted patterns only in terms of denial of service, and recommended a timeout for them. It did not clearly say whether compiling an untrusted pattern is a use case that Ruby supports. We have since discussed this and decided that memory corruption reachable by compiling an untrusted pattern is a vulnerability in Ruby, which is why we have published the advisories above.</p>

<title>Ruby 4.1.0-preview1 Released</title>
<description>
<p>We are pleased to announce the release of Ruby 4.1.0-preview1.
Ruby 4.1 introduces Ractor local GC, Windows support of YJIT, autoload_relative,
and adds many improvements.</p>
<h2 id="ractor-improvements">Ractor improvements</h2>
<p>A lot of work has gone into making Ractors more stable, performant, and usable. These improvements bring Ractor implementation closer to leaving experimental status.</p>
<ul>
<li>
<p>The default GC now runs <strong>per Ractor</strong>: each Ractor collects its own heap
on its own thread without stopping the others, and a stop-the-world
collection only runs when it is really needed (explicit full <code class="language-plaintext highlighter-rouge">GC.start</code>,
shareable-object growth, reclaiming dead Ractors’ heaps). Allocation-heavy
Ractor programs now scale like forked processes.</p>
</li>
<li>
<p>
<code class="language-plaintext highlighter-rouge">GC.start(global: false)</code> can be used when multiple Ractors are running to force
a Ractor-local GC. By default, <code class="language-plaintext highlighter-rouge">GC.start</code> runs a global GC (all Ractors) like
before. This can also be triggered with <code class="language-plaintext highlighter-rouge">GC.start(global: true)</code>. The <code class="language-plaintext highlighter-rouge">global</code>
keyword argument has no effect when a single Ractor is running.</p>
<p>Visible behavior changes:</p>
<ul>
<li>
<code class="language-plaintext highlighter-rouge">Ractor#value</code> returns the value only once; a second call raises
<code class="language-plaintext highlighter-rouge">Ractor::Error</code>.</li>
<li>
<code class="language-plaintext highlighter-rouge">GC.disable</code>/<code class="language-plaintext highlighter-rouge">GC.enable</code> act as per-Ractor holds on a process-wide
switch: one Ractor’s <code class="language-plaintext highlighter-rouge">GC.enable</code> no longer overrides another Ractor’s
<code class="language-plaintext highlighter-rouge">GC.disable</code>.</li>
<li>
<code class="language-plaintext highlighter-rouge">ObjectSpace.each_object</code> enumerates the calling Ractor’s own objects
plus other Ractors’ shareable objects (<code class="language-plaintext highlighter-rouge">ObjectSpace.dump_all</code> still
covers everything).</li>
<li>
<code class="language-plaintext highlighter-rouge">ObjectSpace.define_finalizer</code> on another Ractor’s object raises
<code class="language-plaintext highlighter-rouge">Ractor::IsolationError</code>.</li>
</ul>
</li>
<li>
<p>
<code class="language-plaintext highlighter-rouge">Ractor#monitor</code> now sends an Array naming the Ractor and what happened to
it, <code class="language-plaintext highlighter-rouge">[ractor, :exited]</code> or <code class="language-plaintext highlighter-rouge">[ractor, :aborted]</code>, where it used to send the
bare Symbol <code class="language-plaintext highlighter-rouge">:exited</code> or <code class="language-plaintext highlighter-rouge">:aborted</code>. Several Ractors can then report to one
port and the receiver still knows which one finished. The Array is built for
the receiving Ractor, so watching many Ractors leaves no shareable objects
behind.</p>
<div class="language-plaintext highlighter-rouge">
<div class="highlight">
<pre class="highlight">
<code>r = Ractor.new { :ok }
r.monitor(port = Ractor::Port.new)
port.receive #=&gt; [r, :exited]
</code>
</pre>
</div>
</div>
<p>One port can therefore watch a whole group, which is all a supervisor
needs:</p>
<div class="language-plaintext highlighter-rouge">
<div class="highlight">
<pre class="highlight">
<code>workers.each { |r| r.monitor port }
until workers.empty?
r, status = port.receive
workers.delete(r)
workers &lt;&lt; restart(r) if status == :aborted
end
</code>
</pre>
</div>
</div>
</li>
</ul>
<h2 id="language-changes">Language changes</h2>
<ul>
<li>
<p>
<code class="language-plaintext highlighter-rouge">super</code> in a module method that was called via <code class="language-plaintext highlighter-rouge">super</code> from a refinement
method now works correctly.
[<a href="https://bugs.ruby-lang.org/issues/22309">Feature #22309</a>]</p>
</li>
<li>
<p>
<code class="language-plaintext highlighter-rouge">Module#clone</code> and <code class="language-plaintext highlighter-rouge">Module#dup</code> no longer rewrite the lexical scope of
copied methods. Constants and class variables resolve through the
original class, consistent with inheritance and mixins.
[<a href="https://bugs.ruby-lang.org/issues/21981">Feature #21981</a>]</p>
</li>
<li>
<p>
<code class="language-plaintext highlighter-rouge">alias</code> and <code class="language-plaintext highlighter-rouge">Module#alias_method</code> in a module emit a deprecation warning
when the original method is not a method of the module or its ancestors
and is only found through the fallback to <code class="language-plaintext highlighter-rouge">Object</code>. The fallback will be
removed in Ruby 4.3, and such an alias will raise a <code class="language-plaintext highlighter-rouge">NameError</code>.
[<a href="https://bugs.ruby-lang.org/issues/22276">Bug #22276</a>]</p>
</li>
<li>
<p>
<code class="language-plaintext highlighter-rouge">alias</code> and <code class="language-plaintext highlighter-rouge">Module#alias_method</code> emit a deprecation warning when the
original method is defined in a prepended module. This behavior will
be removed in Ruby 4.3, and alias lookup will start at the origin
class (after prepended modules).
[<a href="https://bugs.ruby-lang.org/issues/22273">Bug #22273</a>]</p>
</li>
</ul>
<h2 id="core-classes-updates">Core classes updates</h2>
<p>Note: We’re only listing outstanding class updates.</p>
<ul>
<li>
<p>C API</p>
<ul>
<li>
<code class="language-plaintext highlighter-rouge">RB_NOGVL_PENDING_INTR_FAIL</code> is added as a flag for <code class="language-plaintext highlighter-rouge">rb_nogvl</code>.
<code class="language-plaintext highlighter-rouge">rb_nogvl</code> does not enter the blocking region (and does not call the
given function), returning <code class="language-plaintext highlighter-rouge">0</code>, if the current thread has pending
interrupts, including interrupts masked by <code class="language-plaintext highlighter-rouge">Thread.handle_interrupt</code>.
As with the existing skip path, <code class="language-plaintext highlighter-rouge">errno</code> is <code class="language-plaintext highlighter-rouge">0</code> because the function was
never called.</li>
<li>
<code class="language-plaintext highlighter-rouge">RHASH_TBL</code> is deprecated. [<a href="https://bugs.ruby-lang.org/issues/22232">Feature #22232</a>]</li>
</ul>

<p>Array</p>
<ul>
<li>
<code class="language-plaintext highlighter-rouge">Array#pack</code> accepts new formats <code class="language-plaintext highlighter-rouge">R</code> and <code class="language-plaintext highlighter-rouge">r</code> for unsigned and signed
LEB128 encoded integers. [<a href="https://bugs.ruby-lang.org/issues/21785">Feature #21785</a>]</li>
<li>
<code class="language-plaintext highlighter-rouge">Array#pack</code> accepts new formats <code class="language-plaintext highlighter-rouge">x!</code> and <code class="language-plaintext highlighter-rouge">@!</code> to align the current

</ul>

<p>ENV</p>
<ul>
<li>
<code class="language-plaintext highlighter-rouge">ENV.fetch_values</code> is added. It returns an array of values for the

<li>
<p>GC</p>
<ul>
<li>
<code class="language-plaintext highlighter-rouge">GC.stat</code> accepts <code class="language-plaintext highlighter-rouge">scope: :ractor</code> (the default), <code class="language-plaintext highlighter-rouge">scope: :local</code>
(a synonym for <code class="language-plaintext highlighter-rouge">:ractor</code>), and <code class="language-plaintext highlighter-rouge">scope: :global</code>.
With the default collector, the global scope reports cumulative collection
counts and measured marking/sweeping CPU time across Ractors, including
history from destroyed object spaces, without requesting a stop-the-world
snapshot. Unscoped <code class="language-plaintext highlighter-rouge">GC.stat</code>, <code class="language-plaintext highlighter-rouge">GC.count</code>, and <code class="language-plaintext highlighter-rouge">GC.total_time</code> retain their
current-Ractor behavior.</li>
<li>
<code class="language-plaintext highlighter-rouge">GC.stat</code> reports a new key, <code class="language-plaintext highlighter-rouge">:global_gc_count</code>: the number of
stop-the-world global garbage collection cycles the current Ractor
initiated. Each global collection is attributed to exactly one Ractor,
so the values sum across Ractors. <code class="language-plaintext highlighter-rouge">GC.stat(:global_gc_count,
scope: :global)</code> reports the process total, including the counts of
terminated Ractors.</li>
<li>A global garbage collection is not counted in <code class="language-plaintext highlighter-rouge">:major_gc_count</code>.
<code class="language-plaintext highlighter-rouge">:count</code> equals <code class="language-plaintext highlighter-rouge">:minor_gc_count</code> plus <code class="language-plaintext highlighter-rouge">:major_gc_count</code> plus
<code class="language-plaintext highlighter-rouge">:global_gc_count</code> in both scopes. When another Ractor’s object space
exists, including one left by a terminated Ractor that is not yet
absorbed, or one was absorbed since the last global collection,
<code class="language-plaintext highlighter-rouge">GC.start</code> runs a global collection by default, so it increments
<code class="language-plaintext highlighter-rouge">:global_gc_count</code> rather than <code class="language-plaintext highlighter-rouge">:major_gc_count</code>; pass <code class="language-plaintext highlighter-rouge">global: false</code>
for a local major collection.</li>
<li>Global compaction no longer counts overlapping CPU intervals in scalar GC
timing statistics. Profiler wall-time intervals are unchanged.</li>
</ul>

<ul>
<li>
<p>Support code for the following platforms has been removed. Their
vendors or distributors have ended support, there is no environment to
test Ruby on them, and none of them has a platform maintainer.</p>
<ul>
<li>AmigaOS</li>
<li>AtheOS</li>
<li>BSD/OS (BSDi)</li>
<li>ESIX</li>
<li>EWS-UX (NEC EWS4800)</li>
<li>FreeBSD, NetBSD and OpenBSD with a.out binaries</li>
<li>GNU/kFreeBSD</li>
<li>GNU/kOpenSolaris</li>
<li>HI-UX/MPP</li>
<li>HP-UX on the HP 9000 Series 300</li>
<li>Interix (Windows Services for UNIX)</li>
<li>IRIX</li>
<li>MirOS BSD</li>
<li>NeXTSTEP, OpenStep and Rhapsody</li>
<li>OSF/1 (Tru64 UNIX)</li>
<li>QNX Neutrino</li>
<li>SunOS 4 (Solaris, i.e. SunOS 5, is unaffected)</li>
<li>System V Release 4</li>
<li>UNICOS/mp (Cray X1)</li>
<li>UX/PDS</li>
</ul>
</li>
<li>
<p>Support code for the following old versions has been removed.</p>
<ul>
<li>Cygwin 1.3 and earlier</li>
<li>Solaris 9 and earlier</li>
<li>Linux 2.6.23 and earlier (RHEL 5)</li>
</ul>
</li>
<li>
<p>Windows 10 1703 or later no longer needs the <code class="language-plaintext highlighter-rouge">LongPathsEnabled</code> registry
value to use paths longer than 260 characters. This applies to any process
running the interpreter, including a program which embeds libruby. Each path
component is still limited to 255 characters, and a child process still
starts with the <code class="language-plaintext highlighter-rouge">MAX_PATH</code> limited current directory. [<a href="https://bugs.ruby-lang.org/issues/18947">Bug #18947</a>]</p>
</li>
<li>
<p>Building Ruby with MSVC now requires Visual Studio 2017 version 15.8
(<code class="language-plaintext highlighter-rouge">_MSC_VER</code> 1915) or later.</p>
</li>
<li>
<p>Ruby built with MSVC now requires Windows 10 version 1809 (build 17763)
or Windows Server 2019 or later. Earlier Windows 10 releases and Windows
Server 2016 are no longer supported.</p>
</li>
<li>
<p>Ruby on macOS now requires Mac OS X 10.6 or later. Mac OS X 10.5 and
PowerPC Macs are no longer supported.</p>
</li>

<h2 id="compatibility-issues">Compatibility issues</h2>
<ul>
<li>
<p>A class or module can now be modified only by the Ractor which created it,
its <em>owner</em>. Defining, removing or undefining methods, <code class="language-plaintext highlighter-rouge">alias</code>, changing
visibility, <code class="language-plaintext highlighter-rouge">include</code>/<code class="language-plaintext highlighter-rouge">prepend</code>, <code class="language-plaintext highlighter-rouge">Module#refine</code>, defining or removing
constants, registering an <code class="language-plaintext highlighter-rouge">autoload</code>, writing the class’s own instance
variables and class variables, <code class="language-plaintext highlighter-rouge">Module#freeze</code> and
<code class="language-plaintext highlighter-rouge">Module#set_temporary_name</code> raise <code class="language-plaintext highlighter-rouge">Ractor::IsolationError</code> in any other
Ractor. Reading is unchanged. Everything defined at boot or by the main
Ractor, <code class="language-plaintext highlighter-rouge">require</code>d libraries included, is owned by the main Ractor, so a
non-main Ractor can no longer monkey-patch it; and since defining a constant
in a foreign class is prohibited, it can not define a top-level class or
module name either. In exchange a Ractor has full use of the classes it
creates itself, including unshareable constant, instance variable and class
variable values, which not even the main Ractor could do before. See
doc/language/ractor.md. [<a href="https://bugs.ruby-lang.org/issues/22226">Feature #22226</a>]</p>
</li>
<li>
<p>
<code class="language-plaintext highlighter-rouge">Kernel#at_exit</code> and <code class="language-plaintext highlighter-rouge">END {}</code> now raise <code class="language-plaintext highlighter-rouge">Ractor::IsolationError</code> when called
in a non-main Ractor. Previously the registered handler ran in the main
Ractor at process exit, which was confusing. [<a href="https://bugs.ruby-lang.org/issues/22139">Feature #22139</a>]</p>
</li>
<li>
<p>
<code class="language-plaintext highlighter-rouge">Ractor.make_shareable</code> now raises <code class="language-plaintext highlighter-rouge">Ractor::Error</code> for an <code class="language-plaintext highlighter-rouge">IO</code> object, and
<code class="language-plaintext highlighter-rouge">Ractor.shareable?</code> returns <code class="language-plaintext highlighter-rouge">false</code> for it. A frozen <code class="language-plaintext highlighter-rouge">IO</code> used to be
shareable, but almost all of its methods raise <code class="language-plaintext highlighter-rouge">FrozenError</code> and it can
still refer to unshareable objects through the members of <code class="language-plaintext highlighter-rouge">rb_io_t</code>.</p>
</li>
<li>
<p>
<code class="language-plaintext highlighter-rouge">Random.urandom</code> now raises <code class="language-plaintext highlighter-rouge">RangeError</code> for every size too large for a
<code class="language-plaintext highlighter-rouge">long</code>, as <code class="language-plaintext highlighter-rouge">Random#bytes</code> does. A size that still fit in an <code class="language-plaintext highlighter-rouge">unsigned long</code>
used to raise <code class="language-plaintext highlighter-rouge">ArgumentError</code>. [<a href="https://bugs.ruby-lang.org/issues/22400">Feature #22400</a>]</p>
</li>
<li>
<p>
<code class="language-plaintext highlighter-rouge">Struct#[]</code> and <code class="language-plaintext highlighter-rouge">Struct#[]=</code> now raise <code class="language-plaintext highlighter-rouge">IndexError</code> for every out-of-range
Integer index that fits in a <code class="language-plaintext highlighter-rouge">long</code>. An index past the <code class="language-plaintext highlighter-rouge">int</code> range used to
raise <code class="language-plaintext highlighter-rouge">RangeError</code>. [<a href="https://bugs.ruby-lang.org/issues/22400">Feature #22400</a>]</p>
</li>
</ul>
<h2 id="stdlib-compatibility-issues">Stdlib compatibility issues</h2>
<ul>
<li>
<p>prism is now a bundled gem. Under Bundler, <code class="language-plaintext highlighter-rouge">require "prism"</code> needs prism
in the Gemfile. Use <code class="language-plaintext highlighter-rouge">Ruby::Prism</code> for the parser of the running
interpreter. [<a href="https://bugs.ruby-lang.org/issues/22379">Bug #22379</a>]</p>
</li>
<li>
<p>
<code class="language-plaintext highlighter-rouge">Etc.getlogin</code> on Windows now returns the login name determined when the
process starts, from the <code class="language-plaintext highlighter-rouge">USER</code> or <code class="language-plaintext highlighter-rouge">USERNAME</code> environment variable or
<code class="language-plaintext highlighter-rouge">GetUserName()</code>. It used to follow later changes to <code class="language-plaintext highlighter-rouge">ENV['USER']</code>.</p>
</li>
<li>
<p>Socket</p>
<ul>
<li>
<p>On Windows, a connection that is refused or unreachable now raises the
matching <code class="language-plaintext highlighter-rouge">Errno</code> class as soon as Winsock reports it, instead of
<code class="language-plaintext highlighter-rouge">Errno::ETIMEDOUT</code> once the whole <code class="language-plaintext highlighter-rouge">connect_timeout</code> has passed. Code
rescuing <code class="language-plaintext highlighter-rouge">Errno::ETIMEDOUT</code> there has to rescue the real error instead.</p>
</li>
<li>
<p>On Windows, <code class="language-plaintext highlighter-rouge">BasicSocket#getsockopt(:SOCKET, :ERROR)</code> now reports an
errno as it does on the other platforms, instead of the raw WinSock
error code. Code comparing it with a <code class="language-plaintext highlighter-rouge">WSAE*</code> value has to compare it
with the matching <code class="language-plaintext highlighter-rouge">Errno::*::Errno</code> instead.</p>
</li>
</ul>
<p>[<a href="https://bugs.ruby-lang.org/issues/18661">Bug #18661</a>]</p>
</li>
</ul>
<h2 id="c-api-updates">C API updates</h2>
<h3 id="embedded-typeddata">Embedded TypedData</h3>
<ul>
<li>
<p>The <code class="language-plaintext highlighter-rouge">RUBY_TYPED_EMBEDDABLE</code> flag is now public and documented and can be used by C extensions.
It allows allocating C structs directly into Ruby object slots, which reduces pointer chasing,
and in some case memory usage.
See the C extension documentation for details. [<a href="https://bugs.ruby-lang.org/issues/21853">Feature #21853</a>]</p>
</li>
<li>
<p>Added new C23 inspired allocator functions, that takes the previous memory size.
This allow the Ruby GC to better keep track of memory usage, improving its heuristics.
It also improves the performance of system allocators that support C23 <code class="language-plaintext highlighter-rouge">free_sized</code>.</p>
<p>However, it is important to note that passing an incorrect size to these function is undefined
behavior and may result in crashes or memory leaks.</p>
<ul>
<li>
<code class="language-plaintext highlighter-rouge">ruby_xfree_sized(void *ptr, size_t size)</code>
</li>
<li>
<code class="language-plaintext highlighter-rouge">ruby_xrealloc_sized(void *ptr, size_t newsiz, size_t oldsiz)</code>
</li>
<li>
<code class="language-plaintext highlighter-rouge">ruby_xrealloc2_sized(void *ptr, size_t newelems, size_t newsiz, size_t oldelems)</code>
</li>
</ul>
<p>[<a href="https://bugs.ruby-lang.org/issues/21861">Feature #21861</a>]</p>
</li>
</ul>
<h3 id="ractor-scoped-gc-address-registration">Ractor-scoped GC address registration</h3>
<ul>
<li>
<p>
<code class="language-plaintext highlighter-rouge">rb_gc_register_address</code> and <code class="language-plaintext highlighter-rouge">rb_global_variable</code> now register the address
with the calling Ractor, and only that Ractor’s GC marks the stored object.</p>
<p>Any Ractor may register an address, but the value stored through it must be a
special constant, a shareable object, or an unshareable object owned by the
registering Ractor. Storing another Ractor’s unshareable object can result in
the object being freed while the address still refers to it (use-after-free).</p>
<p>If the address has process lifetime (a static VALUE), register it from the
main Ractor or keep the stored values shareable.</p>
<p>When the registering Ractor is joined with <code class="language-plaintext highlighter-rouge">Ractor#value</code>, remaining
registrations move to the joining Ractor; otherwise they move to the main
Ractor once the dead Ractor is collected.</p>
<p>[[Feature #22277]]</p>
</li>
</ul>
<h3 id="type-for-lengths-and-indices">Type for lengths and indices</h3>
<ul>
<li>
<p>
<code class="language-plaintext highlighter-rouge">rb_len_t</code> and <code class="language-plaintext highlighter-rouge">rb_ulen_t</code> are added as the types of the lengths and indices
of String, Array and MatchData, with <code class="language-plaintext highlighter-rouge">LEN2NUM</code>, <code class="language-plaintext highlighter-rouge">NUM2LEN</code>, <code class="language-plaintext highlighter-rouge">ULEN2NUM</code>,
<code class="language-plaintext highlighter-rouge">rb_len2int</code>, <code class="language-plaintext highlighter-rouge">PRIdLEN</code> and its siblings, <code class="language-plaintext highlighter-rouge">RB_LEN_MAX</code>, <code class="language-plaintext highlighter-rouge">RB_LEN_MIN</code>,
<code class="language-plaintext highlighter-rouge">RB_ULEN_MAX</code>, <code class="language-plaintext highlighter-rouge">SIZEOF_RB_LEN_T</code> and <code class="language-plaintext highlighter-rouge">HAVE_RB_LEN_T</code>. <code class="language-plaintext highlighter-rouge">RbConfig::SIZEOF["rb_len_t"]</code>
gives its size to an extconf.rb. They are <code class="language-plaintext highlighter-rouge">long</code> on every platform for now, and
the C API that carries such lengths, such as <code class="language-plaintext highlighter-rouge">RSTRING_LEN</code> and
<code class="language-plaintext highlighter-rouge">rb_range_beg_len</code>, uses them. A later change will makes them 64 bits on mswin,
so extensions should keep these lengths in <code class="language-plaintext highlighter-rouge">rb_len_t</code>. [<a href="https://bugs.ruby-lang.org/issues/22400">Feature #22400</a>]</p>
</li>
<li>
<p>
<code class="language-plaintext highlighter-rouge">rb_len2long</code> is added to convert an <code class="language-plaintext highlighter-rouge">rb_len_t</code> to <code class="language-plaintext highlighter-rouge">long</code>, raising
<code class="language-plaintext highlighter-rouge">RangeError</code> via the new <code class="language-plaintext highlighter-rouge">rb_out_of_long</code> when it does not fit, for
extensions that keep a length in <code class="language-plaintext highlighter-rouge">long</code>. [<a href="https://bugs.ruby-lang.org/issues/22400">Feature #22400</a>]</p>
</li>
</ul>
<h3 id="removed-apis">Removed APIs</h3>
<p>The following APIs, which have been deprecated for many years, are removed.
[<a href="https://bugs.ruby-lang.org/issues/21768">Feature #21768</a>]</p>
<ul>
<li>old postponed job functions,</li>
<li>untyped data object type/functions,</li>
<li>old APIs to allocate a data object,</li>
<li>taintedness/trustedness enums/macros,</li>
<li>
<code class="language-plaintext highlighter-rouge">rb_gc_force_recycle</code> function,</li>
<li>
<code class="language-plaintext highlighter-rouge">rb_iterate</code> function,</li>
<li>and some functions and constants for internal use.</li>
</ul>
<h2 id="implementation-improvements">Implementation improvements</h2>
<ul>
<li>
<p>The default garbage collector has been switched from a freelist allocator to a bump pointer allocator. [<a href="https://github.com/ruby/ruby/pull/17201">PR #17201</a>]</p>
</li>
<li>
<p>The error_highlight, did_you_mean, and syntax_suggest gems are now
loaded lazily on the first error display instead of at interpreter
boot, which reduces startup time. <code class="language-plaintext highlighter-rouge">Process.warmup</code> loads them
eagerly so that pre-forking servers keep their code in
copy-on-write shared memory. [<a href="https://bugs.ruby-lang.org/issues/21951">Feature #21951</a>]</p>
</li>
</ul>
<h3 id="mn-thread-scheduler">M:N thread scheduler</h3>
<ul>
<li>
<p>The scheduler scales with the number of waiters and of Ractors, where it
used to walk a list or take one lock for all of them:</p>
<ul>
<li>A timed wait sits in a hierarchical timer wheel rather than on a list
sorted by deadline, which was inserted into by a linear scan.</li>
<li>An fd stays armed in the backend between waits, instead of being added
before each wait and removed after each wake.</li>
<li>The io-wait bookkeeping is sharded by fd, rather than serialized on one
lock across every fd.</li>
<li>A timed wait on an fd rides the scheduler instead of going to a blocking
region, which cost a native thread handoff per wait.</li>
<li>A context switch, and leaving or rejoining the shared pool, no longer take
the scheduler’s global lock.</li>
</ul>
</li>
<li>
<p>The <code class="language-plaintext highlighter-rouge">RUBY_MN_THREADS</code> environment variable now runs from no M:N scheduling
at all to all of it. <code class="language-plaintext highlighter-rouge">-1</code> is new: a Ractor’s threads have been M:N since
the scheduler was added, with no way to turn that off. <code class="language-plaintext highlighter-rouge">0</code> and <code class="language-plaintext highlighter-rouge">1</code> are
unchanged.</p>
<table>
<thead>
<tr>
<th>
</th>
<th>main thread</th>
<th>the main Ractor’s other threads</th>
<th>a Ractor’s threads</th>
</tr>
</thead>
<tbody>
<tr>
<td>
<code class="language-plaintext highlighter-rouge">-1</code>
</td>
<td>1:1</td>
<td>1:1</td>
<td>1:1</td>
</tr>
<tr>
<td>
<code class="language-plaintext highlighter-rouge">0</code> or unset</td>
<td>1:1</td>
<td>1:1</td>

</tr>
<tr>
<td>
<code class="language-plaintext highlighter-rouge">1</code>
</td>
<td>1:1</td>

</tr>
<tr>

<td>M:N</td>
<td>M:N</td>
</tr>
</tbody>
</table>
</li>
<li>
<p>
<code class="language-plaintext highlighter-rouge">RUBY_MN_THREADS=2</code> is new. The main thread is resumed like any other M:N
thread rather than woken on a native thread of its own, which costs an order
of magnitude more. It pays off when the main thread drives the work, and
does nothing for one that only starts other threads and waits.</p>
<p>The main thread is then no longer bound to one OS thread, which is what the
M:N scheduler already meant for every other thread:</p>
<ul>
<li>A C extension that keeps state per OS thread has to call
<code class="language-plaintext highlighter-rouge">rb_thread_lock_native_thread()</code>.</li>
<li>What must run on the process’s initial thread does not work at all,
pinning included: macOS AppKit and CFRunLoop, and hosts that embed Ruby
and return into their own main loop.</li>
</ul>
</li>
<li>
<p>The OS thread name is no longer set from the Ruby thread for M:N threads:
one native thread runs many of them over its life. <code class="language-plaintext highlighter-rouge">Thread#name=</code> was
already skipped for the same reason.</p>
</li>
</ul>
