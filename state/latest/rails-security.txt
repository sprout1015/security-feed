<p>Hello, Rails community!</p>
<p>Rails Versions 8.0.5.2 and 8.1.4.1 have been released. These are <strong>security updates</strong> addressing 21 security issues falling into a few themes:</p>
<ul>
<li>Possible arbitrary file read, file write and remote code execution in Active Storage image and video processing</li>
<li>Possible Strong Parameters bypass in <code>Parameters#each_key</code>
</li>
<li>Possible IP spoofing in <code>remote_ip</code> through the <code>Forwarded</code> header (8.1 only)</li>
<li>Multiple possible XSS vulnerabilities in Action View helpers, and one in the Active Support MessagePack serializer (8.1 only)</li>
<li>Possible DoS vulnerabilities in Active Support <code>safe_constantize</code>, Action Controller Live streaming, and Active Storage proxy mode and filename handling</li>
<li>Unsigned <code>Content-Type</code> and unenforced file size in Active Storage direct uploads to Google Cloud Storage</li>
<li>Session handling issues: a destroyed session restored by <code>CacheStore</code>, a session cookie leaked by Active Storage proxy mode, and a missing <code>SameSite</code> attribute on session cookies</li>
<li>Possible cache poisoning through content negotiation</li>
<li>Possible signature replay in Action Mailbox Mailgun ingress</li>
</ul>
<p>We strongly recommend upgrading as soon as possible.</p>
<p>Older versions of Rails are unsupported, and users are recommended to upgrade to at least the 8.0 series. Security support for the 8.0 series ends on November 7, 2026. See our <a href="https://rubyonrails.org/maintenance">maintenance policy</a> for details.</p>

<title>[GHSA-744p-w4gc-m3gh] SQL injection through `Trilogy#escape` with multibyte encodings</title>
<dc:creator>
<![CDATA[John Hawthorn]]>
</dc:creator>
<category>Security Announcements</category>
<description>
<![CDATA[
<p>
<a href="https://github.com/trilogy-libraries/trilogy/security/advisories/GHSA-744p-w4gc-m3gh">GHSA-744p-w4gc-m3gh</a>
</p>
<p>This is a vulnerability in the Trilogy library which is used by the Active Record Trilogy adapter. We believe it’s likely applications using Trilogy as their MySQL adapter are vulnerable and should upgrade immediately.</p>
<p>This has not yet been assigned a CVE identifier, I will update the report when it is.</p>
<h3>
<a name="p-268238-summary-1" class="anchor" href="https://discuss.rubyonrails.org#p-268238-summary-1" aria-label="Heading link">
</a>Summary</h3>
<p>
<code>Trilogy#escape</code> produces unsafe output for Strings in Shift_JIS, Windows-31J, Big5, GBK or GB18030. In those encodings, the continuation byte of a multi byte character can be in the ASCII range. <code>escape</code> was intended for strict ASCII supersets and did not handle this correctly, which allowed SQL injection.</p>
<h3>
<a name="p-268238-details-2" class="anchor" href="https://discuss.rubyonrails.org#p-268238-details-2" aria-label="Heading link">
</a>Details</h3>
<p>Applications are affected in two cases:</p>
<ol>
<li>On any connection charset, including the default <code>utf8mb4</code>, when an attacker can influence the encoding of a String the application escapes.</li>
<li>On connections configured with <code>encoding: sjis</code>, <code>cp932</code>, <code>big5</code>, <code>gbk</code> or <code>gb18030</code>. These connection encodings never worked correctly, are no longer supported, and now raise <code>ArgumentError</code>.</li>
</ol>
<h3>
<a name="p-268238-impact-3" class="anchor" href="https://discuss.rubyonrails.org#p-268238-impact-3" aria-label="Heading link">
</a>Impact</h3>
<p>Unauthenticated SQL injection in applications that escape attacker-influenced Strings with <code>Trilogy#escape</code>. Ruby on Rails and other Rack applications using the Trilogy adapter are likely affected.</p>
<h3>
<a name="p-268238-workarounds-4" class="anchor" href="https://discuss.rubyonrails.org#p-268238-workarounds-4" aria-label="Heading link">
</a>Workarounds</h3>
<p>Applications unable to upgrade may be able to avoid this issue by enforcing the encoding of all strings passed to <code>Trilogy#escape</code> and <code>Trilogy#query</code>
</p>
<h3>
<a name="p-268238-credit-5" class="anchor" href="https://discuss.rubyonrails.org#p-268238-credit-5" aria-label="Heading link">
</a>Credit</h3>
<p>Discovered by Anthropic’s OSS Scanner, as vulnerability ANT-2026-9KOHJMNW</p>

<title>[CVE-2026-66066] Attack details, and tools to perform a forensic investigation</title>
<dc:creator>
<![CDATA[Mike Dalessio]]>
</dc:creator>
<category>Security Announcements</category>
<description>
<![CDATA[
<p>Hello there, I’m writing as a member of the Rails security team about CVE-2026-66066.</p>
<p>As mentioned in the advisory, <a href="https://github.com/rails/rails/security/advisories/GHSA-xr9x-r78c-5hrm">GHSA-xr9x-r78c-5hrm</a>, we held back details about the attack vector to allow applications to be upgraded before malicious attackers could take advantage of the vulnerability.</p>
<p>We originally intended to publish these details no later than 2026-08-28, but several researchers quickly reverse-engineered the attack and have already published proofs-of-concept. As a result, we are disclosing details about the attack now, along with some tools to help assess whether an application was vulnerable and to help examine the forensic evidence for signs of secret exfiltration.</p>
<p>We have published all of this in a git repository, <strong>
<a href="https://github.com/rails/rails-forensics-CVE-2026-66066">rails/rails-forensics-CVE-2026-66066</a>
</strong>, which contains:</p>
<ul>
<li>
<code>reference/the-attack.md</code> explains how the attack works, step by step, from the incoming request to the file being read.</li>
<li>
<code>reference/the-investigation.md</code> explains what evidence the attack leaves behind in your database and your object store, and what that evidence does and does not prove.</li>
<li>The <code>kr2s-was-i-vulnerable</code> agent skill works out whether your application was ever vulnerable, and if it was, over what period of time.</li>
<li>The <code>kr2s-was-i-exploited</code> agent skill searches your Active Storage data for the crafted files, and works out what was read if it finds any.</li>
</ul>
<p>I sincerely hope you find this information and these tools helpful. They were extracted from work I did at 37signals to perform a forensic analysis on our own apps. And if you have suggestions on how to improve it, I would welcome pull requests that are likely to be generally useful.</p>
<p>We again want to thank the original reporters, 0xacb, s3np41k1r1t0 and castilho of Ethiack, and RyotaK of GMO Flatt Security Inc., for responsibly reporting this vulnerability and for holding off on publishing attack details at our request.</p>

<title>[CVE-2026-66066] Possible arbitrary file read and remote code execution in Active Storage variant processing</title>
<dc:creator>
<![CDATA[Rafael França]]>
</dc:creator>
<category>Security Announcements</category>
<description>
<![CDATA[
<p>See <a href="https://github.com/rails/rails/security/advisories/GHSA-xr9x-r78c-5hrm" class="inline-onebox">Possible arbitrary file read and remote code execution in Active Storage variant processing · Advisory · rails/rails · GitHub</a>
</p>
<h3>
<a name="p-267668-impact-1" class="anchor" href="https://discuss.rubyonrails.org#p-267668-impact-1" aria-label="Heading link">
</a>Impact</h3>
<p>In its default configuration, a Rails application that displays image variants may allow an
unauthenticated attacker to read arbitrary files from the server, including the process environment.
That environment typically holds <code>secret_key_base</code> and often credentials for external systems, which
may in turn allow escalation to remote code execution or lateral movement to those systems.</p>
<h3>
<a name="p-267668-details-2" class="anchor" href="https://discuss.rubyonrails.org#p-267668-details-2" aria-label="Heading link">
</a>Details</h3>
<p>libvips reads and writes file formats through “loaders” and “savers” (or more generally
“operations”), many of which are backed by third-party libraries. It marks some of these operations
as “unfuzzed”, meaning they are unsafe for untrusted content, and several handle formats unrelated
to web images. Active Storage did not disable the unfuzzed operations, so an attacker who can upload
a crafted file and cause a variant to be generated from it may be able to invoke one.</p>
<p>We are aware of a mechanism by which an attacker, by uploading a crafted file, is able to cause
disclosure of the contents of arbitrary files accessible on the filesystem of the targeted
application. One specific attack chain has been reported to us (see “Disclosure” below), but we do
not assume it is the only one that exists.</p>
<h3>
<a name="p-267668-affected-applications-3" class="anchor" href="https://discuss.rubyonrails.org#p-267668-affected-applications-3" aria-label="Heading link">
</a>Affected applications</h3>
<p>An application is affected if it meets all of these requirements:</p>
<ul>
<li>Uses libvips for Active Storage image processing. This is <code>config.active_storage.variant_processor = :vips</code>,
which <code>load_defaults 7.0</code> set and no later default has changed.</li>
<li>Allows image uploads from untrusted users.</li>
</ul>
<p>Generating variants is not a separate requirement.</p>
<h3>
<a name="p-267668-mitigation-4" class="anchor" href="https://discuss.rubyonrails.org#p-267668-mitigation-4" aria-label="Heading link">
</a>Mitigation</h3>
<ul>
<li>Upgrade to a fixed version of <code>activestorage</code>.</li>
<li>The minimum version of libvips must be upgraded to <code>>= 8.13</code>.</li>
<li>Change <code>secret_key_base</code> and change any secrets accessible in the application environment (see “Expire and change secrets” below)</li>
</ul>
<p>Earlier versions of libvips (<code>
< 8.13</code>) cannot disable unfuzzed operations at all, and Active Storage
will raise an exception during boot in such an unsecurable environment.</p>
<h3>
<a name="p-267668-expire-and-change-secrets-5" class="anchor" href="https://discuss.rubyonrails.org#p-267668-expire-and-change-secrets-5" aria-label="Heading link">
</a>Expire and change secrets</h3>
<p>Upgrading closes the vulnerability but does not undo an exfiltrated secret if that already
occurred. An affected application should treat every secret readable by the application process as
potentially exposed and change it, including:</p>
<ul>
<li>
<code>secret_key_base</code>
</li>
<li>The master key, whether stored in <code>config/master.key</code> or supplied as <code>RAILS_MASTER_KEY</code>, along
with everything in <code>config/credentials.yml.enc</code> that it decrypts</li>
<li>Credentials for the Active Storage service, such as S3, GCS, or Azure keys</li>
<li>Database credentials</li>
<li>Tokens and keys for any third-party service the application calls</li>
</ul>
<p>Changing <code>secret_key_base</code> expires active sessions and requires users to log in again. Encrypted
cookies, signed cookies, signed global IDs, and Active Storage URLs are also affected.</p>
<p>Rotation should only be used as an intermediate step if necessary. Do not retain an exposed secret
as a fallback.</p>
<h3>
<a name="p-267668-workarounds-6" class="anchor" href="https://discuss.rubyonrails.org#p-267668-workarounds-6" aria-label="Heading link">
</a>Workarounds</h3>
<p>If libvips <code>
< 8.13</code> is being used, there are no workarounds available other than removing the
dependency on libvips from the application. Some applications may have <code>ruby-vips</code> declared as a
dependency only for image analysis, and those applications may be able to simply remove <code>ruby-vips</code>
from the Gemfile to remove libvips from the application. Applications that do not use Active Storage
can remove <code>ruby-vips</code> from the Gemfile to avoid the boot-time checks.</p>
<p>If libvips <code>>= 8.13</code> is present on the system, applications can disable the unfuzzed operations
without upgrading Rails by setting the <code>VIPS_BLOCK_UNTRUSTED</code> environment variable, which libvips
reads while initializing.</p>
<p>Applications also running ruby-vips <code>>= 2.2.1</code> or later can instead call
<code>Vips.block_untrusted(true)</code> from an initializer.</p>

<dc:creator>
<![CDATA[Mike Dalessio]]>
</dc:creator>
<category>Security Announcements</category>
<description>
<![CDATA[
<p>See <a href="https://github.com/rails/rails-html-sanitizer/security/advisories/GHSA-cj75-f6xr-r4g7" class="inline-onebox">Possible XSS vulnerability with certain configurations of rails-html-sanitizer · Advisory · rails/rails-html-sanitizer · GitHub</a>
</p>
<h2>
<a name="p-267563-summary-1" class="anchor" href="https://discuss.rubyonrails.org#p-267563-summary-1" aria-label="Heading link">
</a>Summary</h2>
<p>There is a possible cross-site scripting vulnerability in rails-html-sanitizer when the sanitizer is configured to allow an SVG reference element such as <code>
<use>
</code>. See related <a href="https://github.com/flavorjones/loofah/security/advisories/GHSA-9wjq-cp2p-hrgf">GHSA-9wjq-cp2p-hrgf</a> in Loofah, whose SVG local-reference logic rails-html-sanitizer mirrors.</p>
<ul>
<li>Versions affected: <code>>= 1.0.3, < 1.7.1</code>
</li>
<li>Not affected: <code>
< 1.0.3</code>
</li>
<li>Fixed versions: <code>1.7.1</code>
</li>
</ul>
<h2>
<a name="p-267563-impact-2" class="anchor" href="https://discuss.rubyonrails.org#p-267563-impact-2" aria-label="Heading link">
</a>Impact</h2>
<p>
<code>Rails::HTML::PermitScrubber</code> restricts SVG reference elements in the <code>SVG_ALLOW_LOCAL_HREF</code> collection to local, same-document references, but that restriction covered only the <code>xlink:href</code> attribute. Browsers also accept a plain <code>href</code> attribute per the SVG 2 spec, and it was not restricted, so those elements could reference arbitrary external documents. SVG <code>
<use>
</code> can load and render external SVG content by reference, and if the referenced document is same-origin and contains scripts, it could execute in the context of the sanitized document. <code>
<feImage>
</code> can load external images, which can be used for tracking.</p>
<p>Applications are impacted only when the allowed tags are overridden to include one of these SVG reference elements, for example <code>
<use>
</code> or <code>
<feImage>
</code>. The default allowed tags do not include these SVG elements, so applications using the default configuration are not affected.</p>
<h2>
<a name="p-267563-workarounds-3" class="anchor" href="https://discuss.rubyonrails.org#p-267563-workarounds-3" aria-label="Heading link">
</a>Workarounds</h2>
<p>Remove the SVG reference elements (such as <code>use</code> and <code>feImage</code>) from the overridden allowed tags. Applications using the default allowed tags are not affected.</p>
<h2>
<a name="p-267563-references-4" class="anchor" href="https://discuss.rubyonrails.org#p-267563-references-4" aria-label="Heading link">

</li>
<li>
<a href="https://cwe.mitre.org/data/definitions/79.html">CWE-79: Improper Neutralization of Input During Web Page Generation (‘Cross-site Scripting’)</a>
</li>
<li>CVE has been requested</li>
</ul>

<title>[CVE-2025-24293] Active Storage allowed transformation methods potentially unsafe</title>

<category>Security Announcements</category>
<description>
<![CDATA[
<p>Active Storage attempts to prevent the use of potentially unsafe image
transformation methods and parameters by default.</p>
<p>The default allowed list contains three methods allowing for the circumvention
of the safe defaults which enables potential command injection
vulnerabilities in cases where arbitrary user supplied input is accepted as
valid transformation methods or parameters.</p>
<p>This has been assigned the CVE identifier CVE-2025-24293.</p>
<p>Versions Affected: >= 5.2.0
Not affected: < 5.2.0
Fixed Versions: 7.1.5.2, 7.2.2.2, 8.0.2.1</p>
<ul>
<li>CVE-2025-24293</li>
<li>GHSA-r4mg-4433-c7g3</li>
</ul>
<h2>
<a name="p-265310-versions-affected-1" class="anchor" href="https://discuss.rubyonrails.org#p-265310-versions-affected-1" aria-label="Heading link">
</a>Versions affected</h2>
<ul>
<li>activestorage >= 8.0, < 8.0.2.1 (patched in 8.0.2.1)</li>
<li>activestorage >= 7.2, < 7.2.2.2 (patched in 7.2.2.2)</li>
<li>activestorage >= 0, < 7.1.5.2 (patched in 7.1.5.2)</li>
</ul>
<h2>
<a name="p-265310-impact-2" class="anchor" href="https://discuss.rubyonrails.org#p-265310-impact-2" aria-label="Heading link">
</a>Impact</h2>
<p>This vulnerability impacts applications that use Active Storage with the image_processing processing gem in addition to mini_magick as the image processor.</p>
<p>Vulnerable code will look something similar to this:</p>
<pre data-code-wrap="ruby">
<code class="lang-ruby">
<%= image_tag blob.variant(params[:t] => params[:v]) %>
</code>
</pre>
<p>Where the transformation method or its arguments are untrusted arbitrary input.</p>
<p>All users running an affected release should either upgrade or use one of the workarounds immediately.</p>
<h2>
<a name="p-265310-releases-3" class="anchor" href="https://discuss.rubyonrails.org#p-265310-releases-3" aria-label="Heading link">

<h2>

<p>Consuming user supplied input for image transformation methods or their parameters is unsupported behavior and should be considered dangerous.</p>
<p>Strict validation of user supplied methods and parameters should be performed as well as having a strong <a href="https://imagemagick.org/script/security-policy.php">ImageMagick security policy</a> deployed.</p>

</ul>
<p>
<em>Mike Dalessio</em>
</p>
</li>
<li>
<p>The tags “noscript”, “mglyph”, and “malignmark” will not be allowed, even if explicitly added to
the allowlist. If applications try to allow any of these tags, a warning is emitted and the tags
are removed from the allow-list.</p>
<p>The CVEs addressed by this change are:</p>
<ul>
<li>CVE-2024-53988 (<a href="https://github.com/rails/rails-html-sanitizer/security/advisories/GHSA-cfjx-w229-hgx5" class="inline-onebox">Possible XSS vulnerability with certain configurations of rails-html-sanitizer 1.6.0 · Advisory · rails/rails-html-sanitizer · GitHub</a>)</li>
<li>CVE-2024-53989 (<a href="https://github.com/rails/rails-html-sanitizer/security/advisories/GHSA-rxv5-gxqc-xx8g" class="inline-onebox">Possible XSS vulnerability with certain configurations of rails-html-sanitizer 1.6.0 · Advisory · rails/rails-html-sanitizer · GitHub</a>)</li>
</ul>
<p>Please note that we <em>may</em> restore support for allowing “noscript” in a future release. We do not
expect to ever allow “mglyph” or “malignmark”, though, especially since browser support is minimal
for these tags.</p>
<p>
<em>Mike Dalessio</em>
</p>
